# 元画像の画線が支持する閉じ括弧を単行APIでも保持する

## 実装前仕様

`docs/literal_closers_probe.md` の固定583画像×30/50/100、1749個の一回のrawから比較した。
元の正読184入力が単行の括弧削除で崩れ、画素支持の保持で104入力を完全一致へ戻せた。
一律保持は73文字指標、108単語指標で退行する。トークン確率.99を使う探索案も退行した。
例はfullwidthの `A）BC` をモデルが高確率で `A) BC` と出すケースで、文字幅と空白の誤りが残る。
確率や文書種類だけで保持する方法は採用しない。

今回の実装は、画像を持つstateless/Session/Poolの単行認識が、同じrawのページ断片候補を
選択肢として持つ。元の単行結果より文字数が多く、空白を含まず、実効方向が横書きであり、
正しいRGB長・寸法と既存の独立画線群の文字数支持を満たす場合だけ候補を保持する。
単純な括弧バランスだけで、画像が支持するrawの閉じ括弧を削らない。
文字の追加/推測置換、追加モデル/追加forwardは行わず、元RGBとconfidenceを変更しない。
無効画像・方向不一致・画素不足・空白を含む曖昧な候補には従来結果を保持する。
text-only sanitizer、未処理/候補API、ページ断片の処理とページ経路は変更しない。

最初は既存の独立成分の文字数支持だけを使う。和文字形の複数成分や低い角括弧など、
raw正読でも支持が得られない80入力は未解決として残し、目的全体をこの範囲へ縮めない。
幅/空白・複雑字形への別手法は追加検証してから扱う。

先に7字形の `111111)` / `)111111` が6字になる純粋Redを更新し、各括弧種・未支持/空白/不正RGB・方向・PBTを追加する。
実画像でも生出力にある括弧を落とす各公開APIのRedを先行する。
採用は全583×3モデル×none/width/strict=5247文字/単語指標で非悪化を要求する。
既存263の全789 CLI本文とrawから構成した前結果は既にbyte一致し、新320の960 before CLIも同様に確認する。
afterの全1749 CLIを新規実行して同じrawからの候補と照合し、scalar/batch/Poolとraw/候補/エラー/再利用を検査する。
ページは全poolがfragment方針を使うことと、その実装・呼出sourceの一致を検査し、モデル回帰も通す。
新fixtureの原画素・文字列は変更せず、全CSV/MD・生トークン確率・失敗案・source/binary/model SHAを保存する。
