# URL/パスの行末ハイフンを保持する

## 原因（実装前）

固定神戸市資料の既定CLIと `--structure-rules false` を比較すると、rawの
`https://www.jmanet.go.jp/kobe-` / `c/press/...` が既定では `.../kobec/press/...`
へ変わる。第二URLでも同じ。これは一般英文の `implemen-` / `tation` 向け処理が
URLのliteralなハイフンを削除するためで、モデル自身の脱落とは区別できる。
ドメイン内の別の欠落 (`jma-net`→`jmanet`) はこの施策で補正しない。

## 仕様（実装前）

`join_latin_hyphenated_lines` の結合候補の末尾の空白区切りtokenに
`://`、`www.`で始まる表記、または `/`、`\\` のパス区切りがある場合、
英文の印刷ハイフネーションと見なさず、元の二行とハイフンを保持する。
URLの全文検証・補完、空白の削除、複数行URLの自動再構成はしない。

URLより後ろに空白を隔てた英文が続く場合、その末尾の通常の英単語は従来どおり
結合する。schemeの大小文字、footnote/ラベルの有無に依存しない。
URL/パスの文字列を作り替えるルールや資料固有の置換をコアへ足さない。

URIか分からない普通の `word-` だけの継続は従来どおり。前行以前のURI状態を
推測して別の英文へ伝播させない。この段階では `mailto:` 等、上記の見える構造を
持たない識別子の完全分類は保証しない。

## 先行検証

合成のURL/パス/footnote、通常英文の対照、プロパティを先にRed化する。
固定実資料CLIでは元RGBのURL開始2行が行末 `kobe-` のまま残ることを要求する。
文書内容を使う分岐は加えず、モデル入力と結果の生成は不変とする。

固定20画像（元5資料+JPEG90/75/半分PNG）×DEIM/bands×前後の80プロセスを
全件評価し、画像ごとのnone/width/strictの文字距離がすべて非悪化であることを
採用ゲートとする。前版は5a8dad9で固定する。モデル/charset SHAと全本文を保存し、
条件を結果ごとに調整しない。通常/ONNX回帰、fmt/Clippyも検証する。

## Red / Green と全件評価

単体5件中3件のRed（URL・パス・URLのPBT）を確認し、最小の末尾tokenガードで
5件Green。通常英文と、URLの後ろの英文・Unicodeの接頭辞も既存どおり結合する。
実モデルCLIのRed→DEIM/bands両方Greenも確認した。

全80プロセスが成功。前版の全40本文を再現し、各画像のnone/width/strict計120指標は
すべて非悪化。神戸市の原/JPEG90/JPEG75は両検出器、半分PNGはDEIMだけ変化する。
変化した7組はURL2本のハイフンと物理改行の保持だけで、他33組はbyte同一。
原画像の既定DEIMは生74→70、width26→22、strict58→56 /1034字。
bandsは生78→74、width29→25、strict60→58。

構造処理無効の実画像本文が前後でbyte同一であることを別途確認。
通常499件・ONNX対象411件、fmt/diff/対象Clippyが成功（既存17警告）。
既存の96合成cropの生モデル/選択結果も前版と一致する。
証拠一式は `benchmarks/url-hyphen/` に保存。新しい推論や画素加工はない。

残るドメイン内hyphen/URL内underscoreの脱落はモデル/入力側であり、
今回の文字列保持とは分ける。次は原100文字cropと寸法に適合する安全なchunkを
比較し、情報量やリサイズの差による欠落を診断する。
