# P0: Page返却枠と字形BBoxの診断（追加NN・実装前）

## 出発点

Oは73e9ab4へ反映し、remote CIを確認中である。全444 Page IDの前後8経路は本文/平均bits不変だった。
直接Fragmentで回復したN新規7画像にも、Page30/defaultでは1..7文字の誤りが残る。
`PageRecognizer::from_pools`はFragment方針を使い、DEIM枠の認識はAutoである。
方向経路の欠落と決めつけず、元56x1628などの入力と返却枠46x1612などの違いを先に調べる。

## この段階だけの固定範囲

- N/N2新規144画像の全model30/50/100・eval/default、計864 Page結果を除外せず扱う。
  本文108画像は元generatorの字形BBoxを使う。残る36図形の空GTは診断規約のまま保つ。
- 保存したPage返却枠を元PNGへ適用し、モデル/GTを使わずRGBと寸法/SHAを保存する。
  同じRGB/寸法は共有し、モデル/設定/行indexごとの対応は失わない。空のPage結果も残す。
- 原画像と全元glyph BBoxを保持する。各枠について、全包含・部分交差・枠外のglyphを記録する。
  部分交差を除外して「安全」と数えない。bbox内の白領域であっても字形BBoxを切る枠は区別する。
- 返却枠は後段context選択を通ったものである。最初のParseq入力やraw本文と等しいと仮定せず、
  この結果は「返却領域を再構成したproxy」と明記する。実入力/元raw/分割の棄却理由は必要なら別の固定診断で観測する。
- 元NNと同じ全画素をPIL/Rustのcrop規約（exclusive x1/y1）で検査する。出力/GTをstripしない。

純粋な枠分類・原画素cropの小さなRed/Greenを先行する。この段階は製品処理、Oの条件、検出枠を変更しない。
新規モデルload/認識/内部forwardは0。改善や採用を宣言せず、得た原因を次の施策の事前仕様へ使う。
既知font/既知結果に対する原因調査であり、新規holdout有効性の検証とは扱わない。
