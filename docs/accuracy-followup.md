# PR #21 後の精度改善

## 実装前の評価方針（2026-10-18）

基準は main b490ade（PR #21）。Phase 1〜5 の既存実装と固定公式モデルを維持し、
新しい実資料から検出・分割・認識の誤りを切り分ける。文字列による文書固有の
置換はコアへ追加しない。採用する挙動ごとに仕様→失敗テスト→最小変更とする。

最初の追加資料は気象庁 2026-03-13 神戸市発表区域変更のお知らせ
https://www.jma.go.jp/jma/press/2603/13b/20260313_oshirase.pdf 。
既存の奈良市資料と同系統なので、独立した様式のholdoutとは呼ばない。
初回推論前にPDF由来の正解を描画と照合し、本文領域・RGB・真値・SHA256を固定する。
ロゴの英文は本文から除き、範囲は推論結果を見て変更しない。

固定30文字モデル・実入力寸法・横向き生認識・既定の背景処理/帯検出/分割/連結で
基準本文、行座標、各chunkと推論数を保存する。初回の全文一致テストをRedとし、
構造的な欠落とモデル誤認を区別してから合成・負例・有効なPBTを追加する。
精度比較には tools/eval_ocr_metrics.py の none/width/strict を併記する。
画像別非悪化を要求し、合計値で退行を相殺しない。既存の実モデル回帰も実行する。
探索後の入力は開発用回帰となり、未知資料精度の証拠とは区別する。

改善案が失敗したら、条件・結果・棄却理由を記録する。改善できたという結論を
局所テストだけから出さず、既存回帰と全文指標が揃ってから採用する。

## 下線で白列が塞がれる行の分割（実装前仕様）

新規資料の4つのURL帯は、既存APIが安全な白列を見つけられずエラーになる。
比較用全文は、エラー帯だけ全幅を1回認識する明示的診断fallbackで保存する。
これは既存製品の動作だとは主張しない。初回切り抜きの下端が最後のURLを
切っていたため、1710→1740へ延長した（初回/修正後hashを残し、真値は不変）。

通常分割が失敗した横書きだけ、行高12以上・下1/4に長さ8行高以上の連続した
細い水平画線があれば、分割判定用の画像でその画線だけ白として扱う。
画線の行は連続し、厚さは max(1, 行高/12) 以下。残る本文が高さ1/2以上、
高さ1/3以上かつ幅2行高以下の独立列群6個以上を支持する場合だけ認める。
通常分割に成功する行、上部/中央の線、太い線、少数/巨大な単一字形は変更しない。

判定用画像へ既存分割を適用し、成功した場合だけ元座標の区間を返す。
認識RGB・文字列は変えず、下線も含む全画素の被覆と順序を維持する。
白列という既存保証には「このfallbackでは確認された水平画線だけを横切る」
例外が加わる。strictな split_line は変えない。分割不能時の元のエラーも保持する。
実画像4帯・合成/負例・拡大/移動PBTを先にRed化し、実モデルで全文距離と
既存回帰を比較する。URL完全一致は採用の前提とせず、残るモデル誤りを記録する。

## 下線の初回結果

合成/実画像/PBT 3件のRed（負例1件は既存Green）→4件Green。
行ごとの比較で先頭28行は同一、URL4行は全て生/width距離が厳密改善。
全32行の生距離210→82/1034文字、width距離161→33/1034文字。
分割失敗4→0、診断fallbackとの推論数比較121→134。
WERは生35→38/41で悪化する。URL全体を単語扱いするため、欠落したURLを
多く復元しても、残るunderscore誤認で空白が生じると語数距離が増える。
文字列補正は加えず、この制約と生本文を保存する。完全一致の探索Redは未解決。

固定モデル回帰には、URLの最初の行と2つの長いパスの先頭を保護し、分割不能の
診断fallbackを一度も必要としないことを要求する。全文完全一致が必要な探索は
NDLOCR_FOLLOWUP_REQUIRE_EXACT=1 で引き続き実行できる。

## 複数行を囲む左右の縦罫線（実装前仕様）

新規資料の囲み本文の先頭では、左枠の断片が22x26のchunkとなり `0.00` を幻覚する。
本文4行の帯が左右とも x=28/962 の縦枠を含んでいる。既知開発入力の次の対象とする。

行検出の最終段で、両端の細い連続した縦画線が同じ上下範囲（差は行高1/4以内）で
3行高以上続き、少なくとも3つの既存帯の全高をまたぐ場合だけ、囲みの側線候補とする。
線幅は max(1, 行高/12) 以下、囲み幅は8行高以上。本文との完全白の間隔が各側に
行高1/4以上あり、内側には高さ1/3以上・幅2行高以下の列群6個以上を要求する。
元RGBは変更せず、各帯の左右境界を内側本文の端から2pxへ縮める。上下座標は不変。
単独縦画/片側線/太い線/短い枠/少数字形は変更しない。両検出経路を同じ関数で処理する。

先に実資料の枠除外・合成3行・負例・拡大/左右移動PBTのRedを確認する。
下線改善後を基準に行ごとの生/width非悪化と既存実モデル回帰を要求する。
局所的な枠除外が成功しても、認識が悪化すれば採用しない。

### 枠の初回案は退行のため棄却

左右枠の条件だけでは、行5の生19→13/width7→1の一方、行7の中点が欠落し
生5→6/width0→1となり、行別非悪化に失敗した（`frame-model.log`）。
全行一律のtrimは採用しない。本文との余白が少なくとも片側で1行高以上ある行へ
限定する。枠断片が単独chunkになりうる大きな余白に対象を絞り、近い枠の行は
既存モデル文脈を維持する。これを先行の実画像負例テストへ追加してRedを確認する。

### 枠の限定案の結果

近い枠の先行Red→Green。最終案は帯5と8の左右だけ変更し、本文変更は帯5だけ。
行5の生19→13/width7→1、他31行の全文は同一。下線改善後から全文82→76字、
width33→27字へ改善し、基準から210→76 / 161→27となる。帯数32不変、
診断基準121→最終133推論。URL残差・他のモデル誤認・改行/幅差は未解決。

## 下線除去の認識側診断（実装前）

分割判定から下線を外すとURLを復元できるが、実認識ではunderscoreが空白になり、
ドメインのhyphenも1件欠ける。同じ帯・区間・寸法・モデル・charsetを固定し、
長い下線の行だけ白へ置き換えた候補を原RGBと比較する。これは診断限定であり、
字形と重なる画素を保護できる証明がないため製品の正規化へは組み込まない。
初めに既存のURL完全一致Redを固定し、候補で全4行が非悪化かつ合計厳密改善を
満たすかを測る。失敗したら実装を採用せず、その結果を保存する。

### 下線の認識側除去は棄却

同一区間・同一crop寸法の診断では、URL4行のwidth誤りは0/4/1/5→1/0/1/1。
合計10→3でも、原画像で正読した行28のhyphenが欠落し、行別非悪化に失敗した。
モデルへ渡すRGBの下線除去は採用しない。診断テストはこの改善と退行の両方を
保護し、NDLOCR_UNDERLINE_PROBE_REQUIRE_EXACT=1 で未解決の完全一致Redを実行する。
NDLOCR_UNDERLINE_PROBE_REMOVE_RULE=1 で下線除去候補へ切り替える。既定製品の変更なし。

## CLI回帰の追加ゲート（推論前）

局所APIの結果をCLIの改善と混同しないため、baseline b490adeのGit archiveと現在の
コミットを同じCargo.lock・debug profile・公式モデル・CPU intra thread=1でビルドする。
同梱evalの3画像を全件使用し、(1)CLI既定のDEIM/cascade/structure_rules、(2)同条件で
--use-deim-detection false の2設定を比較する。モデル/charsetだけ取得先のmodels/へ明示する。
全画像・各設定それぞれでnone/width/strictの文字距離が非悪化することを要求する。
この評価は既知開発データで、速度測定・未知資料holdoutとは扱わない。

### CLI回帰の結果

3画像×2設定×2版の12プロセスが成功し、全6組の出力テキストはbyte単位で同一。
none/width/strictの画像別18組も不変。CLI全体の精度改善は確認できなかった。
`docs/benchmarks/accuracy-followup/cli/` に生本文、scorer出力、実行argv、終了状態、
binary SHA256とlock SHA256を保存する。
初回は共用targetの古い実行ファイルが残って両binaryが同じhashになったため棄却した。
currentのlibrary/binを再ビルドし、baselineに枠関数symbolがなくcandidateにあることと
異なるbinary hashを確認し、コピーした固定binaryで12件すべてを再実行した。
