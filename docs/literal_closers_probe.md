# 印字された閉じ括弧と、モデルが余計に出す閉じ括弧を分離する

## 推論前仕様

d6a67feの画像付き単行APIは、rawが `111111)` を出しても、対応する開き括弧がないという
テキスト上の理由だけで `)` を落とす。行の前後に文脈がある入力では正しい閉じ括弧も消える。
前段の純粋テストにも、この既知の欠落を維持する期待値が残っている。
モデルが閉じ括弧を誤追加する場合もあるため、一律保持を採用する前に全件で分離する。
製品の変更はこの診断では行わない。text-only sanitizerとページ断片の方針は対象外。

画像は最初のOCRより先に固定する。括弧5組 `() / （） / 「」 / 『』 / 【】` に対し、
body `ABC / 123456 / 資料` のprefix/suffix/先頭1字後の内部/対応した括弧で囲む4配置を作る。
各組に単独closerと `ABC` にcloser2個を加え、計70文字列。閉じ括弧削除の対象でない
`ABC / 123456 / 資料 / ABC] / ]ABC / ABC} / }ABC / ABC. / 資料。 / ABC?` の10対照を加える。
80文字列×角ゴシック/明朝×PNG/JPEG75=320画像、28px、白紙余白8px。
文字列そのものをliteral truthとし、OCR結果を見て画像/真値/条件を変更しない。
font自体は再配布せず、generator/Pillow/font/画像/真値/ZIPのSHAと寸法を記録する。

通常のRust fixtureテストで全組合せ・truth・画像decode・全640 memberを検査するRedを先行する。
既存の単行263画像・図形対照にも同じ30/50/100、Autoでrawを記録する。
合計583画像×3モデル=1749入力に対して、同じrawを使い、現在の画像付き単行処理と
既存fragment処理を比較する。候補・confidence・原RGB・現在/比較textを全件保存する。
現在の処理で構成した既存789本文が、前段の実CLI本文とbyte一致することを確認してから診断へ使う。

none/width/strictの文字/単語指標を全件記録する。rawに元々ない括弧を推測挿入する案は扱わない。
生の正読を後処理が壊すケース、モデル段階で誤読するケース、削除が改善するケースを区別する。
素朴な一律保持と、既存の画素文字数支持による保持候補を独立に測り、真値で候補を選択しない。
合成フォントの開発対照であり、未知の独立資料holdoutや製品精度改善とは数えない。
結果を読んだ後、採用候補の次仕様・失敗テストと公開API/batch/CLIの実モデル検証を先行する。

同じ一回のforwardから、各stepの上位2トークンと確率・停止理由も保存する。
`ParseqCandidateResult.recognition` は共通raw decoderの結果であり、候補確率を正解率とは扱わない。
画素数保持案の最初の診断は既存の横向きAuto条件と同じ連結成分支持を使い、
対応しない和文/単独の閉じ括弧が残るかも全件で明示する。

## 捕捉後の探索と制限

最初のrawを読んだ後に、画素支持または全未対応closer確率が .5/.7/.9/.99 以上という
探索gridを追加した。この閾値探索は事前登録の比較ではない。いずれも退行があり棄却し、
全結果を保存する。モデル間の合意や高確率は、括弧の幅違い・挿入空白の正しさを保証しなかった。
画素支持に加え「候補が空白を含まない」を要求する実装前仕様を後続文書に記し、
CLI全件と公開APIで別途確認する。80件のraw正読がなお回復しないことも記録する。
